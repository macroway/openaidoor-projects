# 技术方案：微信客户询价截图整理工具（MVP）

## 1. MVP 目标与边界

### 要解决的问题
销售人员每天花约 2 小时手动整理微信聊天截图中的客户询价信息。本工具将这一流程自动化：上传截图 → AI 自动提取 → 去重与矛盾消解 → 网页编辑 → 导出 Excel。

### 本次明确不做
- 自动给客户发送追问消息
- 对接库存/订单/业务系统
- 云端多用户协作与权限管理
- 历史询价记录查询和对比
- 语音消息识别
- 数据持久化存储（数据库）

## 2. 技术栈

| 技术 | 解决的问题 | 选择理由 |
|------|-----------|---------|
| **Python 3.11+** | 后端主语言 | 生态成熟，AI SDK 支持好，初学者友好 |
| **FastAPI** | Web 后端框架 | 轻量、现代、自带 API 文档，学习成本低 |
| **豆包视觉模型 API** | 截图文字识别 + 结构化信息提取 | 用户选定；OpenAI 兼容接口，支持图片理解；国内访问友好 |
| **React + Vite** | 前端单页应用 | 组件化开发，生态丰富，适合表格编辑场景 |
| **openpyxl** | 生成 Excel 文件 | Python 最成熟的 xlsx 生成库，支持多 Sheet、样式 |
| **Docker + docker-compose** | 本地部署 | 一键启动，环境一致，无需手动配置 |
| **Uvicorn** | ASGI 服务器 | 轻量，配合 FastAPI 使用 |

**不引入的技术（及理由）**：
- 数据库（SQLite/PostgreSQL）：MVP 数据仅存在于单次会话中，无需持久化
- 消息队列：单用户本地部署，不存在并发压力
- 前端状态管理库（Redux/Zustand）：数据量小，React useState 足够
- 微服务/多容器编排：单体应用即可满足

### 各模块职责

| 模块 | 职责 |
|------|------|
| `routers/upload.py` | 接收前端上传的图片文件，校验格式和大小，存到临时目录，返回文件列表 |
| `routers/process.py` | 接收"开始整理"请求，异步启动解析任务，提供进度查询接口 |
| `routers/export.py` | 接收前端编辑后的最终数据，调用 excel_builder 生成 xlsx 并返回下载 |
| `services/ai_parser.py` | 将图片编码为 base64，构造 Prompt，调用豆包视觉 API，解析返回的 JSON |
| `services/dedup.py` | 按客户名称 + 商品名称分组，合并同一客户同一商品的多条记录，执行矛盾消解 |
| `services/excel_builder.py` | 将最终数据写入双 Sheet Excel，设置列宽、样式 |
| `services/task_manager.py` | 维护任务状态（待处理/进行中/完成/失败），记录进度百分比 |
| `prompts/extract_prompt.py` | 管理发给豆包的结构化提取 Prompt 模板 |
| `config.py` | 从环境变量/.env 读取配置（API Key、模型名、并发数等） |

## 4. 用户流程与数据流

### 用户操作流程

```
打开浏览器 → 进入工作台页
    ↓
拖拽/选择上传截图（1~N 张）
    ↓
点击「开始整理」
    ↓
等待处理（进度条实时更新）
    ↓
自动跳转到结果页
    ↓
预览表格，编辑单元格、删除行
    ↓
点击「导出 Excel」→ 浏览器下载 .xlsx 文件
```

### 数据流（从上传到导出）

```
[前端] 用户上传图片
    │
    ├─ POST /api/upload  ──→  [后端] 保存图片到临时目录
    │                          返回 file_id 列表
    │
[前端] 用户点击「开始整理」
    │
    ├─ POST /api/process  ──→  [后端] 创建任务，开始异步处理
    │                              │
    │   GET /api/task/{id}/status   ├─ 逐张读取图片 → base64 编码
    │   ←── 返回进度 ──────────     ├─ 调用豆包 API 提取结构化数据
    │                              ├─ 按客户名称分组
    │                              ├─ 执行去重与矛盾消解
    │                              ├─ 识别缺失/不确定信息
    │                              └─ 存储结果到内存（task_manager）
    │
[前端] 轮询进度，完成后跳转结果页
    │
    ├─ GET /api/task/{id}/result ──→  [后端] 返回解析结果 JSON
    │
[前端] 用户编辑表格
    │
    ├─ POST /api/export  ──→  [后端] 接收编辑后的数据
    │                          ├─ 调用 excel_builder 生成 xlsx
    │                          └─ 返回文件下载流
    │
[前端] 触发浏览器下载
```

## 5. 主要数据对象

### 5.1 单条询价记录（InquiryRecord）

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|---------|
| id | string (UUID) | 记录唯一标识 | 自动生成 |
| customer_name | string | 客户名称 | 非空；无法识别时为"未知客户" |
| product | string | 商品名称 | 非空 |
| spec | string | 规格（颜色、尺寸、型号等） | 可为空 |
| quantity | string | 数量 | 可为空；支持"100（第一批60+第二批40）"格式 |
| target_price | string | 期望价格 | 可为空；未提及时为"-" |
| delivery | string | 交期和到货地 | 可为空 |
| urgency | enum | 紧急度 | 取值：普通 / 较急 / 紧急 |
| missing_info | string | 缺失信息描述 | 无缺失时为空 |
| source_text | string | 原文依据（关键片段） | 可为空 |
| confidence | object | 各字段置信度标记 | AI 返回，用于标注不确定项 |

### 5.2 人工确认问题（ConfirmItem）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string (UUID) | 唯一标识 |
| customer_name | string | 对应客户 |
| issue | string | 问题描述（哪项信息缺失或不确定） |
| suggestion | string | 建议的追问内容 |

### 5.3 任务状态（Task）

| 字段 | 类型 | 说明 |
|------|------|------|
| task_id | string (UUID) | 任务 ID |
| status | enum | pending / processing / completed / failed |
| total_images | int | 总图片数 |
| processed_images | int | 已处理图片数 |
| records | list[InquiryRecord] | 解析结果 |
| confirm_items | list[ConfirmItem] | 人工确认问题 |
| error_message | string | 失败时的错误信息 |
| created_at | datetime | 创建时间 |

### 5.4 保存位置与删除方式

- **截图文件**：上传后保存在后端临时目录（`/tmp/uploads/{task_id}/`），任务结束或下次上传时自动清理
- **解析结果**：保存在后端内存中（task_manager 的字典），进程重启后丢失
- **前端编辑后的数据**：仅存在于浏览器内存，导出时发送给后端生成 Excel
- **删除方式**：用户可逐个移除文件列表中的文件；任务完成后临时文件由后端自动清理

## 6. 前后端配合与外部服务接入

### 前后端交互方式

- 前端通过 HTTP REST API 与后端通信（JSON 格式）
- 进度查询采用轮询方式（每 2 秒请求一次），MVP 阶段不引入 WebSocket
- 所有 API 路径以 `/api/` 为前缀

### 豆包视觉 API 接入

- **接口地址**：`https://ark.cn-beijing.volces.com/api/v3/chat/completions`
- **协议**：OpenAI 兼容格式（Chat Completions API）
- **认证**：Bearer Token（火山引擎 API Key）
- **图片传入方式**：base64 编码（`data:image/png;base64,...`），避免需要公网 URL
- **推荐模型**：`doubao-vision-pro-32k-241028`（视觉理解专业版）或更新的版本
- **请求示例**：

```json
{
  "model": "doubao-vision-pro-32k-241028",
  "messages": [
    {
      "role": "user",
      "content": [
        { "type": "text", "text": "<结构化提取 Prompt>" },
        { "type": "image_url", "image_url": { "url": "data:image/png;base64,<base64>" } }
      ]
    }
  ]
}
```

### Prompt 设计要点

发给豆包的 Prompt 需要包含：
1. 角色设定：你是一个微信聊天截图解析助手
2. 任务说明：从截图中提取客户询价的结构化信息
3. 输出格式要求：严格返回 JSON，包含指定字段
4. 特殊规则：
   - 区分客户消息（左/白色气泡）和销售消息（右/绿色气泡）
   - 识别截图顶部的客户名称
   - 如果信息模糊或不确定，在对应字段标注 `"_uncertain": true`
   - 如果信息缺失，对应字段返回 `null`
   - 提取关键原文片段作为依据

## 7. 异常场景处理

| 场景 | 处理方式 |
|------|---------|
| **AI 调用超时** | 单张图片设置 30 秒超时；超时后自动重试 1 次；仍失败则标记该图片为"处理失败"，继续处理其他图片 |
| **AI 返回格式异常** | 尝试解析 JSON；解析失败时重试 1 次（Prompt 中追加格式纠正提示）；仍失败则标记该图片为"解析失败"，在结果页提示用户 |
| **API 限流（429）** | 控制并发数（默认 3 个并发调用）；遇到 429 时指数退避重试（2s → 4s → 8s），最多重试 3 次 |
| **网络中断** | 捕获网络异常，标记任务为失败，前端显示错误信息和"重试"按钮 |
| **重复上传相同图片** | 通过文件 MD5 去重，提示用户"该图片已上传" |
| **图片模糊/无法识别** | AI 返回结果中客户名称为 null 时，标记为"未知客户"，列入人工确认 |
| **客户改单（矛盾消解）** | 同一客户 + 同一商品的多条记录合并，以时间最后一条为准（由 AI 在提取时标注消息顺序，后端 dedup 模块执行合并） |
| **同一客户咨询多个商品** | AI 在提取时拆分为多条记录，每条对应一个商品 |
| **处理过程中用户关闭页面** | 后端任务继续执行；用户重新打开后通过 task_id 查询结果（MVP 阶段 task_id 存在内存中，进程重启后丢失） |

## 8. 非功能性设计

### 8.1 性能

- **并发调用 AI**：后端使用 `asyncio` + `httpx.AsyncClient` 并发调用豆包 API，默认 3 路并发（可配置），充分利用 API 限额
- **图片预处理**：上传时检查图片大小，超过 4MB 的图片在前端压缩后再上传（减少网络传输和 API 调用时间）
- **流式进度**：每处理完一张图片即更新进度，前端实时反映
- **目标**：500~1000 张截图 ≤ 15 分钟（主要取决于 AI API 响应速度）

### 8.2 可扩展性

- **模型可切换**：AI 调用层封装为统一接口（`ai_parser.py`），通过配置切换模型名，未来可替换为其他模型
- **Prompt 外置**：Prompt 模板放在独立文件中，方便调优而不改代码

### 8.3 安全性

- **API Key 保护**：通过环境变量传入，不硬编码在代码中，不提交到版本控制
- **数据不持久化**：截图和解析结果仅在内存/临时目录中，进程重启即清除
- **HTTPS**：AI API 调用走 HTTPS 加密通道
- **前端无认证**：MVP 单用户本地部署，暂不做登录认证（后续云端版本再加）

### 8.4 可观测性

- **后端日志**：使用 Python `logging` 模块，记录每次 AI 调用的耗时、token 消耗、成功/失败状态
- **前端错误提示**：处理失败时在页面上显示明确的错误信息和操作建议
- **成本追踪**：日志中记录每次 API 调用的 token 数，便于估算每日费用

## 10. 部署方式

### 运行环境

- Docker Desktop（用户本地笔记本安装即可）
- 无需 GPU
- 需要网络连接（调用豆包 API）

### 启动方式

```bash
# 1. 克隆项目后，复制环境变量模板
cp .env.example .env

# 2. 编辑 .env，填入豆包 API Key
# DOUBAO_API_KEY=your-api-key-here

# 3. 一键启动
docker-compose up --build

# 4. 浏览器访问
# http://localhost:3000
```

### 架构

- `docker-compose.yml` 定义两个服务：
  - `backend`：Python FastAPI 应用，端口 8000
  - `frontend`：Nginx 托管 React 静态文件，端口 3000，反向代理 `/api` 到 backend
- 前端构建产物由 Docker 在构建阶段生成

### 密钥与配置管理

| 配置项 | 来源 | 说明 |
|--------|------|------|
| DOUBAO_API_KEY | .env 文件 | 豆包 API Key，不提交到 Git |
| DOUBAO_MODEL | .env 文件（有默认值） | 模型名称，默认 `doubao-vision-pro-32k-241028` |
| AI_CONCURRENCY | .env 文件（有默认值） | AI 并发调用数，默认 3 |
| MAX_FILE_SIZE | .env 文件（有默认值） | 单文件最大 MB，默认 10 |

## 11. 实现计划

### 第一步：项目初始化与基础框架

- **目标**：搭建前后端项目骨架，能跑通一个空页面
- **涉及模块**：整个项目结构、Docker 配置
- **具体内容**：
  1. 创建后端 FastAPI 项目，包含基本路由和健康检查接口
  2. 创建前端 React + Vite 项目，包含两个空页面（工作台、结果页）和路由
  3. 编写 `docker-compose.yml`，一键启动前后端
  4. 编写 `.env.example` 和 `config.py`
- **完成标准**：`docker-compose up` 后，浏览器访问 `localhost:3000` 能看到工作台页面
- **依赖**：无

### 第二步：文件上传功能

- **目标**：实现截图上传、文件列表展示、拖拽交互
- **涉及模块**：`routers/upload.py`、`UploadZone.jsx`、`FileList.jsx`、`Workspace.jsx`
- **具体内容**：
  1. 后端实现 `POST /api/upload` 接口，接收图片文件，校验格式/大小，存到临时目录
  2. 后端实现 `DELETE /api/upload/{file_id}` 接口，删除已上传文件
  3. 前端实现拖拽上传区域和文件列表（参考设计稿 `workspace-upload.html`）
  4. 前端调用上传 API，展示文件列表和状态
- **完成标准**：用户可以拖拽/选择上传多张截图，文件列表正确显示，可以删除单个文件
- **依赖**：第一步

### 第三步：AI 解析核心

- **目标**：调用豆包 API 从截图中提取结构化询价信息
- **涉及模块**：`services/ai_parser.py`、`prompts/extract_prompt.py`、`models/schemas.py`
- **具体内容**：
  1. 编写结构化提取 Prompt（定义输出 JSON 格式、字段说明、特殊规则）
  2. 实现 `ai_parser.py`：读取图片 → base64 编码 → 调用豆包 API → 解析返回 JSON
  3. 实现错误处理：超时重试、格式异常重试、限流退避
  4. 定义 Pydantic 数据模型（InquiryRecord、ConfirmItem）
- **完成标准**：给定一张测试截图，能返回包含客户名称、商品、规格、数量等字段的结构化 JSON
- **依赖**：第一步（需要 config.py 读取 API Key）

### 第四步：去重、矛盾消解与缺失识别

- **目标**：将多张截图的解析结果合并、去重、消解矛盾、标注缺失
- **涉及模块**：`services/dedup.py`、`services/task_manager.py`
- **具体内容**：
  1. 实现按客户名称 + 商品名称分组
  2. 同一组内多条记录合并：以 AI 标注的消息顺序为准，后出现的覆盖先出现的（数量、颜色、规格、仓库等）
  3. 分批交货处理：数量取总数，交期栏记录分批信息
  4. 缺失信息识别：检查每条记录的必填字段，未提及的列入 ConfirmItem
  5. 不确定信息标注：AI 返回 `_uncertain: true` 的字段列入 ConfirmItem
  6. 实现 task_manager：管理任务状态和进度
- **完成标准**：使用测试截图，输出符合 PRD 预期的 3 条记录 + 3 条人工确认
- **依赖**：第三步

### 第五步：处理流程串联与进度展示

- **目标**：将上传 → 解析 → 去重串联为完整流程，前端展示实时进度
- **涉及模块**：`routers/process.py`、`ProgressBar.jsx`、`Workspace.jsx`
- **具体内容**：
  1. 后端实现 `POST /api/process`：接收文件列表，创建任务，异步执行解析
  2. 后端实现 `GET /api/task/{task_id}/status`：返回进度（已处理/总数/百分比）
  3. 后端实现 `GET /api/task/{task_id}/result`：返回解析结果
  4. 前端实现进度条组件，轮询进度接口
  5. 处理完成后前端自动跳转到结果页
- **完成标准**：上传截图 → 点击"开始整理" → 进度条实时更新 → 完成后跳转结果页
- **依赖**：第二步、第四步

### 第六步：结果页表格展示与编辑

- **目标**：在结果页展示解析后的表格，支持在线编辑
- **涉及模块**：`Results.jsx`、`InquiryTable.jsx`、`ConfirmTable.jsx`
- **具体内容**：
  1. 实现双 Tab 切换（询价整理表 / 人工确认问题）
  2. 实现表格渲染，参考设计稿 `workspace-results.html`
  3. 实现 contenteditable 单元格编辑
  4. 实现行删除功能
  5. 实现统计栏（记录数、待确认数、异常数）
  6. 实现底部工具栏（编辑计数、导出按钮）
- **完成标准**：结果页与设计稿一致，可以编辑任意单元格、删除行
- **依赖**：第五步

### 第七步：Excel 导出

- **目标**：将编辑后的数据导出为双 Sheet Excel
- **涉及模块**：`services/excel_builder.py`、`routers/export.py`
- **具体内容**：
  1. 后端实现 `POST /api/export`：接收前端编辑后的最终数据
  2. 使用 openpyxl 生成 xlsx：Sheet 1 询价整理表（9 列）、Sheet 2 人工确认问题（3 列）
  3. 设置列宽、表头样式、紧急度单元格颜色
  4. 返回文件流，前端触发下载
- **完成标准**：导出的 Excel 格式与 PRD 描述一致，内容以用户编辑后的版本为准
- **依赖**：第六步

### 第八步：端到端测试与调优

- **目标**：使用 PRD 提供的测试样例验证完整流程，调优 Prompt
- **涉及模块**：全部

  2. 逐字段对比实际输出与 PRD 预期结果
  3. 如有偏差，调整 Prompt（这是最可能需要多次迭代的环节）
  4. 测试边界场景（模糊截图、非标准格式、空上传等）
  5. 检查性能是否满足要求（处理速度 ≤ 15 分钟）
- **完成标准**：测试通过率满足 PRD 验收标准（数量准确率 ≥ 99%、去重准确率 ≥ 98% 等）
- **依赖**：第七步

## 12. 风险、取舍与假设

### 风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 豆包 API 对微信截图的识别准确率不够 | 核心功能不可用 | Prompt 反复调优；如仍不够，考虑换用 GPT-4o 视觉模型作为备选 |
| 长截图（多轮对话）超出模型理解能力 | 信息提取不完整 | 必要时将长截图裁切为多段分别处理（增加复杂度） |
| API 调用成本超预期 | 用户经济负担 | 日志记录 token 消耗，提供成本预估；可选用 lite 版本模型降低成本 |
| 截图质量差异大 | 部分截图无法识别 | 前端提示用户上传清晰截图；无法识别的标记为"未知客户" |

### 取舍

| 决策 | 选择 | 理由 |
|------|------|------|
| 进度通知方式 | HTTP 轮询（非 WebSocket） | MVP 场景简单，轮询足够，减少复杂度 |
| 数据存储 | 内存（非数据库） | MVP 单用户单次会话，无需持久化 |
| 图片传入方式 | base64（非公网 URL） | 本地部署无公网入口，base64 最简单 |
| 前端状态管理 | React 内置 state（非 Redux） | 数据量小，不需要额外状态管理库 |

### 暂定假设

| 假设 | 验证方式 |
|------|---------|
| 截图分组由 AI 从截图顶部识别客户名称 | 测试样例验证；如识别不准，考虑让用户手动输入客户名 |
| 紧急度由 AI 根据对话语气判断 | 测试样例验证；如不准，增加关键词规则兜底 |
| 处理完成后截图不保留（进程重启即清除） | MVP 阶段可接受；后续如需历史记录再加数据库 |
| 豆包 API 单次调用延迟 ≤ 5 秒 | 实测验证；如延迟过高，调整并发策略或换模型 |

### 仍需决定的问题

| 问题 | 何时决定 |
|------|---------|
| 豆包具体使用哪个版本的视觉模型（pro vs lite） | 第一步实现时，根据成本和准确率测试决定 |
| 是否需要前端图片压缩 | 第二步实现时，根据实际上传速度决定 |
| Prompt 的最终版本 | 第八步测试调优时确定 |
